# Way 产品需求文档

更新日期：2026-10-14

## 1. 产品背景与定位

自由行让旅行者自己决定去哪、玩什么、停留多久。国家广告研究院《新时代文旅品牌发展研究报告：文化赋能·体验驱动·价值引领》引用的 2026 年 Z 世代文旅消费者专项调研（样本量超过 1,000）显示，95.19% 的受访者偏好自由行，6.73% 偏好传统跟团游。这些结果反映了受访者对自主安排行程的偏好。[资料来源：调研解读与原始图表](https://m.adquan.com/detail/0-361045)

自由行规划涉及目的地、活动、交通、住宿和出行准备。Way 希望解决的问题是：用户需要从多处资料中拼出计划，并在需求变化后重新核对相关安排。这是当前产品假设，仍需通过实际使用与用户反馈验证。

Way 定位为 AI 自由行规划工具，将全程路线与每日路书放在同一份可持续调整的旅行计划中。路线呈现全程怎么走，路书说明每天怎么玩、如何衔接及需要准备什么。

## 2. 目标用户与使用场景

主要面向偏好自主安排旅行、会参考线上攻略或 AI 建议的年轻自由行旅客。既包括独自出行，也包括与朋友或家人同行的用户。

| 场景 | 核心需求 |
| --- | --- |
| 尚未确定目的地 | 根据假期、兴趣和预算筛选旅行方向 |
| 已确定国家或城市 | 比较当地玩法，挑选感兴趣的体验 |
| 已有必去地点或预订 | 在已有条件下补齐行程 |
| 希望调整现有计划 | 看清影响，减少重新规划与核对的负担 |
| 行前准备或旅途中查阅 | 快速找到当天安排及所需信息 |

## 3. 产品目标

| 目标 | 对应验收项目（第 7 节） |
| --- | --- |
| 帮助用户根据自身需求，在有差异的方向和体验之间做出选择 | 个性化推荐、要求与选择保留 |
| 让用户用一份计划完成出行准备与逐日查阅 | 首版规划、路线与路书对应、案例操作 |
| 降低行程调整后重新整理相关信息的负担 | 修改落实、要求与选择保留 |
| 减少简单问题和局部修改的等待 | 简单请求速度；同时满足质量与成功率门槛 |

## 4. 核心使用流程

| 阶段 | 用户动作 | 产品输出 |
| --- | --- | --- |
| 描述需求 | 自由说明旅行想法，按需补充信息 | 已记录的旅行条件与必要追问 |
| 发现与选择 | 浏览方向或体验，查看详情、勾选或换一批 | 候选内容与选择清单 |
| 形成计划 | 选择生成路线，或使用直接规划入口 | 全程路线与每日路书 |
| 查阅与带走 | 查看地图、进入某一天、查阅准备事项或导出 | 当天信息与 PDF |
| 调整计划 | 提出修改，查看结果或待确认方案，采用、放弃或撤销 | 更新后的计划或保留的原版本 |

用户可从查阅返回体验选择或继续交流。各阶段的处理条件见第 8 节。

## 5. 功能需求

### 5.1 旅行条件确认（P0）

- 记录出发地、目的地、日期与天数、同行情况、兴趣、预算、交通方式及已有预订。
- 支持用户补充、纠正条件，并围绕影响当前决策的信息追问。

### 5.2 目的地发现与体验选择（P0）

- 根据旅行条件推荐少量、有差异的方向、地区或体验，说明玩法、适合理由、建议时长、交通与预约条件及详情来源。
- 支持查看详情、多选、逐项移除、换一批和直接规划入口。

### 5.3 路线与每日路书（P0）

- 展示全程地点顺序、停留时间、交通方式及每日活动与住宿区域。
- 每日路书提供具体玩法、建议顺序与时长、交通衔接、预约与准备事项及适用的备选安排。
- 解释主要行程取舍，提供住宿区域选择的理由及有依据的粗略费用参考。

### 5.4 行程修改（P0）

- 支持单日活动、地点、城市、天数、节奏、交通及住宿条件的调整，并展示主要变化。
- 支持查看调整方案、确认采用、放弃方案及撤销最近一次修改。

### 5.5 来源与行前事项（P1）

- 在相关日期或地点下展示参考来源、读取状态及待确认事项。
- 提供与具体活动有关的预约、装备、体力、天气和开放条件提醒，区分普通待确认与影响成行的风险，并说明变化时可采用的备选安排。

### 5.6 地图与 PDF（P1）

- 使用固定 2D 区域地图展示地点与日期编号，在桌面及手机上保持地名可读、编号可点，密集标签避让路线，点击范围不小于 44px。
- 全球目的地沿用同一套地形与地名样式；底图按容器比例呈现，已加载的区域可复用，详细底图暂不可用时提供概览与重试。
- 导出包含全程路线、地图、每日路书、住宿建议和行前事项的 PDF，并保留底图数据署名。

### 5.7 交流与等待体验（P1）

- 以体验选择和行程结果为主体，交流入口按需打开，详细检索记录默认收起。
- 展示实际处理步骤与累计耗时，支持取消和重试；处理期间仍可查阅原计划。

### 5.8 保存与旅行切换（P1）

- 在同一浏览器中保存旅行条件、选择和当前计划，支持刷新恢复及旅行切换。
- 保存当前已采用的版本与可撤销的最近一次调整。

## 6. 本版范围与优先级

### 6.1 能力范围

| 优先级 | 范围 |
| --- | --- |
| P0 | 旅行条件确认、方向与体验选择、路线与路书生成、行程修改 |
| P1 | 来源与行前事项、地图与 PDF、交流与进度、保存、旅行切换及撤销 |
| P2 | 完整费用汇总、只读分享链接、历史版本比较 |

P0 是形成与调整计划的核心能力；P1 支持查阅和保存；P2 留待后续版本。

### 6.2 开放范围

| 版本 | 范围 |
| --- | --- |
| Showcase | 公开展示大阪与鸟取、新西兰南岛、大理三个预设案例，提供案例内的选择、生成、查阅和调整 |
| Live | 按自由输入的条件规划旅行，必要时查询资料；目前仅个人本机可用，暂不向公众开放 |

### 6.3 不在本版范围

本版不处理订票、支付、改签和订单取消，不建设旅行社区、多人投票、酒店商品比较或跨设备同步。计划中的交通、住宿和活动建议不代表真实订单。

## 7. 验收标准

Showcase 与 Live 遵循统一的产品规则和交付要求，按适用场景验证：Showcase 检查预设案例的选择、生成、调整、恢复与导出流程；Live 在流程检查之外，验证真实输入下的规划质量、修改落实和完整耗时。以下为目标门槛，公开的成功样本与通过项见[测试报告](testing.md)。

新规划与有效修改批次须预先登记，按首次请求统计；失败、超时或未交付计入分母，复测单独记录，不替换首次结果。解释类请求与实际修改分别统计，修复、恢复或升级后的完整耗时计入，并记录正确完成比例、失败及超时数量和最长耗时。

| 项目 | 目标 | 检查要求 |
| --- | --- | --- |
| 首版规划 | 30–50 个全新 Live 规划请求中，至少 85% 生成合格计划 | 覆盖未定目的地、已定目的地及已有固定安排；推荐理由符合需求，总天数正确，交通衔接合理，主要事实有依据或标明待确认；失败、超时和未生成均计入分母 |
| 路线与路书对应 | 公开 Showcase 的 3 个案例及个人本机 Live 验收中实际交付的计划，逐日一致性通过率均为 100% | 日期、地点、交通及住宿相互对应，每天能查到玩法与必要准备事项；修改后无已删除活动的专属提醒；无特殊准备要求时允许简写，不以篇幅作为合格依据 |
| 个性化推荐 | 至少 5 组同目的地、不同需求的对比检查全部通过 | 差异应体现在地点、活动或交通安排中；只改推荐文案不算通过 |
| 修改落实 | 至少 20 个有效修改请求中，落实率达到 95% | 有效请求指确实需要改动且不与固定条件冲突的请求；路线、路书及相关提醒同步更新，其他固定条件保留才算成功；失败、超时和未更新均计入分母，冲突请求另验确认流程 |
| 要求与选择保留 | 公开 Showcase 与个人本机 Live 实际交付的计划，明确要求遵守率均为 100%；已选体验安排或解释取舍的比例为 100% | 必去、排除项、交通及固定住宿均符合当前已确认条件；跨批选择不遗漏、不重复，冲突须说明并取得用户选择后再改动固定安排 |
| 简单请求速度 | 个人本机版无需新资料的简单请求，中位完成时间不超过 40 秒 | 解释类请求与实际修改分别统计，不能混入较快的解释回复来证明修改达标；同时报告正确完成比例、失败及超时数量、最长耗时，失败不计作完成，自动修复、恢复或升级后的完整耗时计入统计；40 秒是中位门槛，不是每次请求的耗时上限 |
| 案例操作 | 3 个公开案例在桌面和 375px 手机宽度的全部规定流程均通过 | 实际完成跨批选择、生成、修改、地图查看、撤销、刷新恢复和导出；恢复后的选择与计划保持一致，PDF 与当前计划一致 |

个人本机版简单请求的 40 秒要求是中位门槛，不是每次请求的耗时上限。后续性能优化目标为简单修改中位耗时不超过 20 秒，优化期间仍须满足上述质量与成功率要求。

## 8. 规则说明

本节规定各功能在不同条件下如何处理。Showcase 在预设案例范围内执行，Live 根据用户输入执行。

| 规则 | 处理方式 |
| --- | --- |
| 条件生效 | 以用户最新且未撤销的明确条件为准；缺失的日期、人数或预算保持待确认，暂定条件须说明，不凭同行身份推断偏好，已知信息不重复询问。 |
| 固定安排优先 | 先安排已订交通、住宿及必去体验，再补充其他内容；明确排除项与交通限制必须遵守，一般偏好可在说明理由后提出取舍。 |
| 体验选择与补充 | 跨批次选择累积保留，不遗漏、不重复；未勾选不等于拒绝，明确排除的内容不重新加入，补充的体验标为建议，已选内容无法安排时说明具体取舍。 |
| 规划触发 | 默认先提供体验选择；“帮我安排一下”不自动跳过，明确说“直接排路线”或点击直接规划入口时才直接生成路线。 |
| 天数与时间 | 总天数包含去程、返程、中转及跨日交通；抵离日按实际可用时间安排，日期未定时使用“第几天”，各地活动与航班起降按相应当地时间，时差与夏令时需核对。 |
| 路线安排 | 往返覆盖从出发地离开到返回的完整交通，预留接送、中转、抵离和休息时间；避免不必要的折返，不为排满或凑数重复安排活动；交通方式可组合，愿意自驾不必全程租车，不自驾时核对核心体验的替代交通，重要取舍说明理由。 |
| 住宿与费用 | 住宿夜数与抵离日期一致，飞机或列车上过夜不计酒店住宿；费用参考说明人数、天数与包含项目，缺少依据时不编造精确总价、班次、价格或已订状态。 |
| 修改联动 | 路线、地图、路书和相关准备事项使用同一安排；单日修改只联动受影响的内容，删除活动时更新受影响的交通与玩法，清除专属提醒，其余有效安排保留。 |
| 修改生效 | 含已订安排的行程若改变日期、路线、活动、交通或住宿，先展示调整方案，确认后生效；其他一般调整直接更新并可撤销，固定条件冲突须先取得用户选择。 |
| 取消与撤销 | 取消、失败或结果不完整时保留原计划；撤销或放弃的调整不再作为后续规划条件，未确认方案不替换当前版本。 |
| 来源核验 | 优先采用官方或运营方资料，来源只支持其实际包含的内容；链接可打开或已读正文不代表全部事实已核实，关键条件按出行日期核对，日期未定时提供季节性提示而不编造某天天气，资料不足时标待确认或给有依据的替代建议。 |
| 地图定位 | 地点名称及所属区域有可靠依据时才标点，区分城市级示意与地点级定位；不能可靠定位时标待确认，不采用远处同名地点或未经核实的精确坐标，地图不提供道路导航。 |
| 保存与导出 | 每趟旅行独立保存；PDF 使用当前已采用的版本，保留待确认标记，不把预览方案当作已确认计划。 |
| 处理分工 | 已有行程中的问题优先直接回答，简单修改优先快速处理；需要新资料时补查来源，速度优先不免除质量核验，不展示虚构进度。 |
| 交付条件 | 不满足明确要求、固定安排或路线与路书一致性的结果不得采用；首次规划提示未生成，修改保留旧版，并提供重试。 |

例如，用户删除某个徒步地点后，该日的交通、玩法和装备提醒应按“修改联动”同步更新。
